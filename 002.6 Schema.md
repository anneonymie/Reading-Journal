# Reading Journal: Schema (version 4)

Companion to [[002.5 Journaling systems]]. The runnable definition is `schema.sql` (SQLite 3.43+). `test_schema.py` checks every rule below against a real database; run it with `python3 test_schema.py` after any schema change.

## Data folder

```
journal-data/
  journal.db           ← everything structured, plus all Markdown prose
  images/ab/abcd….png  ← all images: entry images, covers, custom emoji (named by content hash)
```

Settings (address, port, data folder location) come from environment variables, so the data folder holds only data.

Moving to the home server means copying this folder. A Markdown export writes one `.md` per work (metadata as frontmatter, journal as dated sections) with relative image links.

## Decisions

- **Formats are a fixed list:** Manga, Manhwa, Manhua, Webcomic, Comic, Light Novel, Web Novel, Novel, Fanfic, Other. Each has a default progress unit that's pre-selected when adding a work. The list lives in a table, so adding a format later is one row, not a code change.
- **One shared tag pool** for works and images. There is no image-only category.
- **One journal per work.** Every entry belongs to exactly one work.

## How each requirement is handled

### Enforced by the database
- **Source IDs:** stored with the source name. One ID per source per work, and the same ID can't be attached to two works.
- **Length:** every work has a unit (default from its format). The total is optional.
- **Rating:** 0.0–10.0, one decimal place.
- **Progress updates:** creating an entry with progress farther along than the series (same unit) moves the series forward once. Editing an entry, even its progress, changes nothing, so correcting an old entry during a reread can't jump the series ahead. Deleting an entry changes nothing. Manual changes on the series page (including a reread reset to 0) are respected.
- **Unit mismatch:** each entry stores its own unit. `journal_entry_progress.progress_valid` is 0 when it doesn't match the series, which drives the `?` and excludes it from stats. Changing the series unit later loses nothing, and switching back restores the entries.
- **Status history:** `status_event` rows; current status is the latest one, even if older events are added later. Rereads are counted from completions.
- **Status entries are a log:** a status-change journal entry stores a snapshot (from → to). Deleting it leaves the history alone, and deleting a history row leaves the entry alone.
- **Timestamps** must be exactly `2026-10-18T14:03:00Z`. Mixed formats would sort in the wrong order, so the Discord import must convert its timestamps.
- **Tag aliases:** an alias resolves to one tag and can't collide with any tag name or other alias, regardless of capitalization, when creating or renaming either.
- **Parent tags:** `tag.parent_id`, nested to any depth. Loops (A inside B inside A) are rejected.
- **CWs:** a tag is a CW if it has a `cw_setting` row, which holds blur and badge settings. The three defaults are pre-loaded. Child tags inherit their parent's CW (e.g. *Gore* under *Violence*). `image_cw` and `work_cw` give one answer for each image and work, so every screen shows the same blur and badge.
- **Tag justifications:** `work_tag.justification_md`.
- **Lists:** each membership has a note and a position. A work appears once per list.
- **Custom fields:** choice fields only accept their defined choices.
- **Relations:** a work can't relate to itself, and "same universe" can't be entered twice in opposite directions.
- **Images:** keyed by content hash, so the same image is stored once. Paths must stay relative and inside the data folder. An image in use as a custom emoji can't be deleted.
- **Discord import:** every imported entry records its Discord message ID, so re-running the import can't duplicate entries.
- **Creators:** one `work_creator` row per person per role. The work form manages `author` (shown as Writer), `artist` and `unspecified` (a name with no role, shown with no label); a person who is both writer and artist has two rows and is shown once as "(Writer and Artist)". The app never stores `unspecified` alongside another role for the same person and work. Other roles (e.g. from an import) are kept when the form is saved.
- **Publishers:** shared between works like creators (`publisher` names are unique regardless of capitals). `work_publisher` links a work to any number of them, with a `position` keeping the order they were entered in.
- **Search indexes** for works (title, alt titles, creators, description, review, notes), journal text and tags update themselves on every change.

### Handled by the app
- **Foreign keys must be switched on for every database connection** (`PRAGMA foreign_keys = ON`). SQLite leaves them off by default, and without them deletes don't cascade and orphan rows are allowed. This is the single most important app-side rule.
- **Status changes** are made on the series page: the app adds a `status_event` and the matching journal entry together, and skips a "change" to the status the work already has.
- **Reset prompts:** Completed → Currently Reading asks whether to reset progress to 0. So does any change to TBR when progress is above 0.
- **Publication dates:** `pub_start` and `pub_end` are saved as `2019` or `2019-04`, built from a year box and a month list. The end can't be before the start (compared only as precisely as both are known). A value saved before the pickers existed in any other form is kept as it was until a year is picked.
- **Journal image order:** `journal_entry_image.position`. Editing an entry can reorder its images; new images go after the existing ones.
- **Completing fills in progress:** a status change to Completed (on the series page, or adding a work as Completed) sets `progress_current` to `length_total` when there is a total. This is app-side rather than a trigger, so importing old status history can't overwrite current progress.
- **Schema versions:** `PRAGMA user_version` is 4. Version 3 removed the trigger that let editing an entry move the series' progress. Version 4 replaced the single `work.publisher` text with the `publisher` and `work_publisher` tables; the upgrade moves each existing publisher across.
- **Source links:** the work form takes pasted links in a list and recognises the site from each one. A bare ID isn't accepted, since a number alone could be from more than one site. Two different links to the same site are refused (one ID per site per work). Earlier `schema.sql` files are kept in `old_schemas/` so upgrades can be tested from a real old database.
- **Progress auto-fill:** a new entry pre-fills with the series' current progress and unit.
- **Grayed-out features:** percentage and completion stats need `length_total`. Progress entry itself is never blocked.
- **Clever tag search:** exact name/alias match → trigram fuzzy match on `tag_search` → similar tags (tags that often appear on the same works). Trigram matching needs at least 3 characters, so 1–2 character queries use a prefix match instead. Aliases always resolve to their canonical tag.
- **Custom field values** other than choices (number, date, URL…) are validated against the field's type.
- **Spoilers, shortcodes and sticker-size emoji** live in the Markdown and are handled at render time. Unicode emoji keywords come from a bundled CLDR annotation file, not the database.
